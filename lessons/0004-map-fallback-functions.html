Map Fallback Functions

Lesson 4 of ? Experimental in 2.4 ~12 min Reference sheet →

The ambiguity in nullable-value maps

A Map<K, V?> — a map whose values can be null — has an invisible trap. When you look up a key and get null back, you don't know which of two very different things happened:

val cache = mutableMapOf<String, String?>("userId" to null)

val result = cache["userId"]    // null — but WHY?
                                  // A: key present, value is null
                                  // B: key absent entirely

For many use cases this doesn't matter. But one case where it matters a great deal: caching nullable results. If your cache returns null and you can't tell whether that's "we already looked this up and it doesn't exist" or "we've never looked this up," you'll re-query the source on every call.

What the existing functions do

getOrElse and getOrPut treat null and absence the same way — both trigger the fallback:

val map = mutableMapOf<String, String?>("key" to null)

map.getOrElse("key") { "fallback" }   // "fallback" — null triggers it
map.getOrElse("other") { "fallback" } // "fallback" — absence triggers it
// no way to tell these two cases apart

For a cache this is broken: every lookup of a stored-null result will re-run the expensive query.

The four new functions

Kotlin 2.4 adds two families, each with a get (read-only) and put (read-and-store) variant:

Function Triggers fallback when… Stores result?
getOrElseIfNull key absent or value is null No
getOrPutIfNull key absent or value is null Yes
getOrElseIfMissing key absent only No
getOrPutIfMissing key absent only Yes

The IfNull family matches the existing getOrElse/getOrPut semantics — it just names the intent explicitly. The IfMissing family is the new semantic: a stored null is a legitimate value, not a miss.

Seeing the difference

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val m1 = mutableMapOf<String, String?>("key" to null)
    val m2 = mutableMapOf<String, String?>("key" to null)

    // IfNull: null value counts as "missing" — replace it
    m1.getOrPutIfNull("key") { "replaced" }
    println(m1)  // {key=replaced}

    // IfMissing: key exists, so null is kept as-is
    m2.getOrPutIfMissing("key") { "replaced" }
    println(m2)  // {key=null}
}
Experimental — requires opt-in Annotate the call site or enclosing function with @OptIn(ExperimentalStdlibApi::class). No compiler flag needed.

The canonical use case: a null-aware cache

The motivating scenario: you query a service that can legitimately return null (user not found, feature disabled, etc.). You want to cache both non-null results and the fact that a lookup returned nothing — so you don't hammer the service on every call.

class UserService {
    var queryCount = 0
    fun find(id: String): User? {
        queryCount++
        return null  // imagine a real DB call that returns null
    }
}

@OptIn(ExperimentalStdlibApi::class)
fun main() {
    val service = UserService()
    val cache   = mutableMapOf<String, User?>()

    fun getUser(id: String): User? =
        cache.getOrPutIfMissing(id) { service.find(id) }

    getUser("abc")              // cache miss → queries service → stores null
    println(cache)              // {abc=null}

    getUser("abc")              // cache hit (null) → does NOT query again
    println(service.queryCount) // 1  ← only one real query
}

With the old getOrPut, queryCount would be 2 — the second call sees null and re-runs the lambda. getOrPutIfMissing distinguishes "stored null" from "absent" and skips the lambda.

Also new: isSorted and friends

Five new stable extension functions for checking sort order on any Iterable, Array, or Sequence:

val numbers = listOf(1, 2, 3, 4)
numbers.isSorted()               // true
numbers.isSortedDescending()     // false

data class User(val name: String, val age: Int)

val users = listOf(User("Alice", 24), User("Bob", 31), User("Charlie", 29))
users.isSortedBy(User::age)           // false — 31 before 29
users.isSortedByDescending(User::age) // false
users.isSortedWith(compareBy { it.name }) // true — alphabetical

Short-circuits immediately on the first out-of-order pair — efficient for large inputs. Returns true for collections with fewer than two elements.

Stable — no opt-in needed All five isSorted* functions are fully stable in 2.4.
