What Swift Export is

Kotlin Multiplatform lets you share Kotlin code across platforms. On Apple targets, that shared code has always needed a bridge into Swift. The old bridge was Objective-C headers — generated automatically by the Kotlin/Native compiler. It worked, but Objective-C interop is verbose, drops Kotlin idioms, and has no concept of coroutines.

Swift Export is the replacement: the compiler generates native Swift API declarations from your Kotlin code directly. You write Kotlin; Swift callers see Swift types, Swift functions, and — since 2.4 — Swift concurrency.

Status: Alpha Alpha means the design is solid enough to build on, but the generated API shape may still change in future releases before it reaches Stable. On by default in 2.4 — no flag needed.

The big addition: suspend → async/await

Before 2.4, coroutines were the main pain point. Kotlin suspend functions are invisible to Objective-C — the bridge couldn't represent them at all, so you had to wrap every suspend function in a callback or a KMP-specific helper library.

In 2.4, Swift Export maps suspend directly to Swift async:

// Kotlin — shared module
suspend fun fetchUser(id: String): User {
    delay(500)
    return User(id, "Alice")
}
// Swift — iOS app
let user = try await fetchUser(id: "u123")
// No callbacks. No wrappers. Just Swift async.

Suspend functional types — lambdas you pass across the boundary — are also exported as Swift async equivalents. Structured cancellation is preserved: if the Swift Task is cancelled, the Kotlin coroutine is cancelled too.

Flow maps to AsyncSequence

kotlinx.coroutines.Flow is Kotlin's reactive stream type. Swift has its own equivalent: AsyncSequence. In 2.4, Swift Export connects them:

// Kotlin
fun stockPrices(ticker: String): Flow<Double> =
    flow {
        while (true) {
            emit(queryPrice(ticker))
            delay(1_000)
        }
    }
// Swift
for try await price in stockPrices(ticker: "AAPL").asAsyncSequence() {
    updateChart(price)
}

The .asAsyncSequence() call is generated by the Swift Export tooling — you don't write it yourself. The element type (Double here) is preserved; Swift infers it without a cast.

Before 2.4, this required third-party bridges like KMMViewModel or SKIE. They're still useful for advanced use cases, but the built-in path now works out of the box.

The Kotlin ↔ Swift concurrency map

Kotlin concept Exported as Swift
suspend fun async func
Suspend lambda suspend () -> T async closure
Flow<T> AsyncSequence (via .asAsyncSequence())
Kotlin exception Swift Error (thrown with try)
Coroutine cancellation Swift Task cancellation (propagated)

Swift Package imports in Gradle

The other major 2.4 addition for KMP: you can now declare Swift Package Manager dependencies directly in your build.gradle.kts, instead of routing them through CocoaPods:

// build.gradle.kts
kotlin {
    swiftPMDependencies {
        swiftPackage(
            url = url("https://github.com/firebase/firebase-ios-sdk.git"),
            version = from("12.11.0"),
            products = listOf(
                product("FirebaseAI"),
                product("FirebaseAnalytics")
            )
        )
    }
}

This replaces the CocoaPods Gradle plugin for Swift-native dependencies. JetBrains provides a migration guide if you're moving an existing project.

What "Alpha" means in practice

Alpha is a meaningful step up from the prior experimental status — JetBrains considers the core design settled. But it isn't Stable:

  • The generated Swift API surface may change between minor versions.
  • Some generic type scenarios may not export cleanly yet.
  • If you ship a public SDK to Swift consumers, pin your Kotlin version carefully until Stable.
  • For internal iOS apps consuming your own KMP module: safe to adopt now.
