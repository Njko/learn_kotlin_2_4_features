Context Parameters

Lesson 1 of ? Stable in 2.4 ~15 min Reference sheet →

The problem they solve

You have a function that needs some ambient object — a logger, a transaction scope, a locale — but it isn't the function's real argument. Passing it explicitly at every call site is noise:

// Every call must thread `logger` through manually
fun processOrder(order: Order, logger: Logger) {
    validateOrder(order, logger)
    chargePayment(order, logger)
    sendReceipt(order, logger)
}

Before 2.4, the common workarounds were extension functions on the context type (Logger.processOrder()), or reaching for a ThreadLocal. Both are awkward: extensions pollute the type, and thread-locals are invisible.

Context Parameters are the language-level answer.

Syntax

Declare a context parameter with context(name: Type) before the function signature:

context(logger: Logger)
fun processOrder(order: Order) {
    logger.info("Processing ${order.id}")  // `logger` is in scope
    validateOrder(order)
    chargePayment(order)
}

To call a function with a context parameter, the required type must be in scope at the call site. You provide it once, and every function in that scope that needs it picks it up automatically:

fun main() {
    val logger = ConsoleLogger()

    with(logger) {           // puts `logger: Logger` in scope
        processOrder(myOrder)  // no explicit logger argument needed
    }
}
Stable in Kotlin 2.4 Context Parameters are fully stable. No compiler flag needed. The one sub-feature still experimental is explicit context arguments (passing context at call site by name) — that needs -Xexplicit-context-arguments.

Multiple context parameters

Declare several in one block:

context(logger: Logger, db: Database)
fun saveUser(user: User) {
    logger.debug("Saving user ${user.id}")
    db.insert(user)
}

All required types must be in scope simultaneously. This composes naturally:

context(logger: Logger, db: Database)
fun createAndSaveUser(name: String) {
    val user = User(name)
    saveUser(user)  // both logger and db are already in scope
}

Context on classes and properties

Context parameters work on class declarations and properties too:

context(scope: CoroutineScope)
class BackgroundSync(val interval: Duration) {
    fun start() {
        scope.launch { /* ... */ }
    }
}

// Instantiate only where CoroutineScope is in scope
context(scope: CoroutineScope)
val sync = BackgroundSync(5.minutes)

Explicit context arguments (experimental)

Sometimes you have two overloads that differ only by context type, and both are in scope — an ambiguity. The new explicit syntax lets you name the context you want:

context(sender: EmailSender)
fun sendNotification() { /* ... */ }

context(sender: SmsSender)
fun sendNotification() { /* ... */ }

context(email: EmailSender, sms: SmsSender)
fun notifyUser() {
    sendNotification(emailSender = email)  // explicit — no ambiguity
    sendNotification(smsSender  = sms)
}
Experimental Requires -Xexplicit-context-arguments and the @OptIn(ExperimentalContextParameters::class) annotation. Not for production yet.

Context parameters vs. extension functions

The key difference: extension functions make the type the receiver, which implies an ownership relationship. Context parameters make it an ambient dependency — the function uses it but doesn't belong to it.

Extension function Context parameter
Logger.processOrder() context(l: Logger) fun processOrder()
Reads as "order processing is part of Logger" Reads as "Logger is needed to process an order"
Pollutes Logger's API surface Keeps Logger clean
Single receiver Multiple contexts supported
