The binary compatibility trap

You publish a library. Version 1.0 ships this function:

// Library v1.0
fun Button(label: String, onClick: () -> Unit) { /* … */ }

A downstream app compiles against v1.0. Its bytecode contains a call to the exact JVM method signature Button(String, Function0).

You add a new optional parameter in v1.1:

// Library v1.1 — naive
fun Button(label: String, color: Color = DefaultColor, onClick: () -> Unit) { /* … */ }

From a source perspective this is backwards-compatible — old callers can recompile and work. But the compiled app from v1.0 is looking for Button(String, Function0) at runtime. That signature is gone. The result is a NoSuchMethodError at runtime — a crash that source compatibility would never catch.

This is binary incompatibility: the compiled contract changed even though the source contract didn't.

The old solutions and their cost

Option 1: Manual hidden overloads

Write the old signature yourself, mark it deprecated at the HIDDEN level so it's invisible to source but present in bytecode:

// Keep old signature alive for pre-compiled callers
@Deprecated("Use Button with color", level = DeprecationLevel.HIDDEN)
fun Button(label: String, onClick: () -> Unit) =
    Button(label, DefaultColor, onClick)

fun Button(label: String, color: Color = DefaultColor, onClick: () -> Unit) { /* … */ }

This works, but you maintain it by hand. Add a third parameter in v1.2 and you need another hidden overload — and another, and another. The boilerplate compounds with each release.

Option 2: @JvmOverloads

@JvmOverloads generates overloads automatically, but for every combination of default parameters, whether or not those combinations represent real historical API states. A function with five defaults gets 32 overloads — most of which serve no compatibility purpose.

@IntroducedAt: version-aware overload generation

Mark each new parameter with the version it was introduced in. The compiler generates exactly the hidden overloads that match your API history — one per version boundary, no more:

@OptIn(ExperimentalVersionOverloading::class)
fun Button(
    label: String = "",
    color: Color = DefaultColor,
    @IntroducedAt("1.1") borderColor: Color  = DefaultBorderColor,
    @IntroducedAt("1.2") borderStyle: Style  = DefaultBorderStyle,
    @IntroducedAt("1.2") borderWidth: Int    = 1,
    onClick: () -> Unit
) { /* … */ }

The compiler reads this history and generates two hidden overloads automatically:

// Generated — invisible to source callers, present in bytecode

// For callers compiled against v1.0 (no border params at all)
fun Button(label: String, color: Color, onClick: () -> Unit) =
    Button(label, color, DefaultBorderColor, DefaultBorderStyle, 1, onClick)

// For callers compiled against v1.1 (borderColor existed, others didn't)
fun Button(label: String, color: Color, borderColor: Color, onClick: () -> Unit) =
    Button(label, color, borderColor, DefaultBorderStyle, 1, onClick)

You write one function. The compiler maintains the history.

The version-boundary model

Each distinct version string in your annotations defines one historical API shape. Parameters sharing a version were introduced together; the compiler treats them as a single change:

Callers compiled against… Overload they receive
v1.0 (original) Button(label, color, onClick)
v1.1 Button(label, color, borderColor, onClick)
v1.2+ (current) Button(label, color, borderColor, borderStyle, borderWidth, onClick)

@IntroducedAt vs @JvmOverloads

@JvmOverloads @IntroducedAt
Overloads generated One per trailing default (combinatorial) One per version boundary (historical)
Visibility Public (visible to source callers) Hidden (bytecode only)
Primary use Java interop convenience Binary compatibility across releases
Can use together? ⚠ Compiler warns — overloads may conflict. @IntroducedAt takes precedence if you suppress the warning.

Who actually needs this

This annotation targets library authors — anyone distributing a compiled artifact that others link against without recompiling. If you control both sides of the dependency (e.g. a monorepo where everything recompiles together), binary compatibility doesn't bite you and you don't need this.

If you maintain an SDK, a design system library, or any published API where consumers pin versions: this replaces a tedious manual process.

Experimental — requires opt-in Annotate each function (or the file) with @OptIn(ExperimentalVersionOverloading::class). The design may still evolve.
