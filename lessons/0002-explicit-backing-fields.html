Explicit Backing Fields

Lesson 2 of ? Stable in 2.4 ~12 min Reference sheet →

The pattern you've seen a thousand times

You want a property that is mutable inside the class but read-only to the outside world. The idiomatic Kotlin solution before 2.4 was the backing property:

class EventBus {
    private val _subscribers = mutableListOf<Subscriber>()
    val subscribers: List<Subscriber> get() = _subscribers

    fun subscribe(s: Subscriber) { _subscribers.add(s) }
}

This works, but it has friction: two declarations for one concept, the _underscore convention as a signal to readers, and a getter that allocates nothing but still has to be written. It also exposes an implementation detail — the "real" list — as a named symbol that can slip into autocomplete.

The explicit backing field

Kotlin 2.4 lets you declare the backing storage as part of the property, on the next line with the field keyword:

class EventBus {
    val subscribers: List<Subscriber>
    field = mutableListOf<Subscriber>()  // type inferred: MutableList<Subscriber>

    fun subscribe(s: Subscriber) { subscribers.add(s) }  // still mutable inside
}

One concept, one declaration. Outside the class, subscribers is a List — the mutable operations simply aren't available. Inside the class the compiler knows the real type and gives you full MutableList access with no cast.

Stable in Kotlin 2.4 No compiler flag needed. IDE support (no red squiggles in IntelliJ IDEA) arrives in IDEA 2026.1.4.

Annotating the field type explicitly

When the inferred type is ambiguous, or you want to be clear about the storage type, name it after field:

class ShoppingCart {
    val items: List<String>
    field: MutableList<String> = mutableListOf()

    fun add(item: String)    { items.add(item) }
    fun remove(item: String) { items.remove(item) }
}

The one rule: field type must be a subtype

The backing field type must be a subtype of the declared property type. That's what makes the internal smart-cast safe — the compiler knows MutableList is a List, so it can expose one face to the outside and another inside.

// ✓  MutableList is a subtype of List
val items: List<String>
field = mutableListOf<String>()

// ✓  MutableStateFlow is a subtype of StateFlow
val count: StateFlow<Int>
field = MutableStateFlow(0)

// ✗  Int is not a subtype of String — won't compile
val label: String
field = 42

When you can't use it

Explicit backing fields are intentionally limited. The property must be:

  • val — not var
  • No custom getter — the whole point is that the field is the getter
  • Not open — can't be overridden in a subclass
  • Not delegated — no by lazy { }, no by viewModels()
  • Not a compile-time constant — no const

If any of these apply, the old backing-property pattern is still your tool.

Real-world pattern: ViewModel with StateFlow

The most immediate use in Android/KMP code: replacing the classic _state/state pair in a ViewModel.

// Before 2.4
class CounterViewModel : ViewModel() {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count.asStateFlow()

    fun increment() { _count.value++ }
}

// Kotlin 2.4
class CounterViewModel : ViewModel() {
    val count: StateFlow<Int>
    field = MutableStateFlow(0)

    fun increment() { count.value++ }  // count is MutableStateFlow inside
}

The _count symbol disappears from the class entirely. No underscore, no .asStateFlow() call, no second declaration.

Comparison with implicit backing fields

Kotlin has always had implicit backing fields, accessed via the field keyword inside custom accessors:

var name: String = ""
    set(value) {
        field = value.trim()  // `field` here is the implicit backing field
    }

That's a different use of the same word. Explicit backing fields are a declaration at the property level — they replace the need for a separate private property. Implicit backing fields are an accessor-level escape hatch. Both remain valid; they solve different problems.
